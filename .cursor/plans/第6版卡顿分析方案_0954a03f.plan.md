# 第6版卡顿分析与优化方案

## 结论

这份日志里，主卡点不在手机互联应用层 H264 队列或 `VDEC_SendStream`，而在录像链启动后的 `MUX/FsWriter` 写盘背压，以及它对整机媒体调度、VE/DDR/I/O 的放大影响。

关键证据：

- 日志显示录像侧在 `16:28:07` 重新拉起后，很快出现 `VENC outputStream timeout` 与 `FsWriter` 单次写盘 `2243ms/2247ms` 的长阻塞，见 [log/第6版运行日志.log](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/log/第6版运行日志.log)。
- 同一份日志中，互联侧 `carplay_display` 统计始终是 `queue_depth=0`、`drop=0`、`retry=0`、`busy=0`，说明应用层喂流和解码线程没有形成堆积。
- `zlink_client` 的 `max_gap_us` 在部分时段冲到秒级，说明“手机视频数据回调到本机的节奏”被外部因素打断，而不是 `carplay_display` 自己喂不进去。

## 责任划分

- 录像侧主责：`RecSinkMuxerInit` 明确打印未使用 `cacheThread`，随后 `Mpeg2tsMuxerWriteHeader` 回退到 `FSWRITEMODE_DIRECT`，再出现 `FsWriter` 秒级写盘阻塞。这是当前最硬的直接证据。
- 互联侧次责：`zlink_client` 与 `carplay_display` 仍有优化空间，但从当前统计看，它们不是“主瓶颈源”，更像是在承受录像侧和系统侧抖动后的受害方。
- SDK/系统侧共责：`wait vbs data timeout`、`VO scaling unsupported`、`736/720` 对齐告警、录像 mux 写模式回退，都属于 Allwinner MPP / CedarX / 存储子系统层面的放大因素。

## 关键代码边界

- 会话参数与手机端协商在 [runcarplay/src/carplay/zlink_client.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/carplay/zlink_client.c)，`session_init()` 里设置 `session_data.width/height/fps` 后调用 `libzlink_init_session_2()`。
- 手机视频回调入口仍是 `video_data_cb()`，active 时直接 `carplay_display_feed_h264()`。
- 互联显示链在 [runcarplay/src/carplay_display/carplay_display.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/carplay_display/carplay_display.c)，`decode_thread_fn()` 负责 `queue_pop -> AW_MPI_VDEC_SendStream`。
- 录像链压力主路径在 [runcarplay/src/app/video/mpp_camera.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/app/video/mpp_camera.c)，核心是 `GetCSIFrameThread -> queue_mpp_push -> Vi2VencFrameThread -> AW_MPI_VENC_SendFrame -> VENC/MUX/FsWriter`。
- 录像侧还存在额外放大项：`FsyncFrameThread()` 每秒 `fsync` 一次目标录像文件，进一步争抢慢存储。
- 录像帧队列实现也有潜在生命周期风险：`queue_mpp_push()` 只存指针，不拷贝 `VIDEO_FRAME_INFO_S`，见 [runcarplay/src/app/video/queue_mpp.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/app/video/queue_mpp.c)。

## 对 `session_data.fps = 30` 的判断

- `session_data.fps = 30` 位于 [runcarplay/src/carplay/zlink_client.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/carplay/zlink_client.c)，这是向手机端请求的目标帧率，不是本地 VDEC 的强制时钟。
- 降到 `25` 或 `20` 只会减少手机侧输出节奏、码率和本地解码压力；如果瓶颈是“互联链自身算力或带宽不足”，会有帮助。
- 但按本日志证据，当前主瓶颈是录像写盘/MUX 背压，因此降 fps 不是第一责任修复项，更适合作为 A/B 验证开关，用来判断互联侧还有多少余量。
- 建议顺序：先做录像侧隔离，再做 `30 -> 25 -> 20` 的对比，观察 `zlink_client max_gap_us`、触摸延迟和录像侧 `FsWriter` 长阻塞是否同步改善。

## 手机互联侧仍可继续优化的空间

- 在 [runcarplay/src/carplay/zlink_client.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/carplay/zlink_client.c) 增加更细粒度的输入节奏统计：把 `video_data_cb()` 的回调间隔按 `p50/p95/max` 输出，区分“手机没来包”还是“本机线程拿不到调度”。
- 在 [runcarplay/src/carplay_display/carplay_display.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/carplay_display/carplay_display.c) 增加 `VO/VDEC` 事件和首帧/卡帧耗时统计，确认卡顿时是否是下游显示卡住而不是输入停了。
- 针对录像并发场景保留一档降载策略：例如 Android Auto 专门请求 25fps，或在检测到 `max_gap_us` 持续超阈值时切低 fps 配置重连验证。
- 继续关注 `736/720` 宽度对齐告警是否在新日志中完全消失；它不是本轮主卡点，但会影响稳定性判断。

## 录像侧最小优先处理项

- 优先确认为什么 [runcarplay/src/app/video/mpp_camera.c](/home/hyby/Desktop/myShare/v853s_sample-new/v853s_sample-new/runcarplay/src/app/video/mpp_camera.c) 明明设置了 `FSWRITEMODE_CACHETHREAD`，运行时仍回退到 `FSWRITEMODE_DIRECT`。这是当前最关键的责任归属点。
- 暂停或降低 `FsyncFrameThread()` 的频率，避免每秒 `fsync` 和 `FsWriter` 长写同时打到存储。
- 复核 `queue_mpp_push()` 的帧生命周期，避免录像链在高压下引入附加抖动或潜在坏帧。

## 执行顺序

1. 先以“录像链主责，互联链次责，SDK/系统共责”作为对外分析口径。
2. 先验证录像侧 `cacheThread` 为何未生效，以及 `fsync` 是否可暂时降频/关闭做 A/B。
3. 在录像侧未收敛前，不把 `session_data.fps` 下调当作主修复，只把它作为互联余量验证项。
4. 若录像侧收敛后仍明显卡顿，再单独做互联侧 `fps 30/25/20` 和更细粒度统计验证。
